# `mvp.md` 입력 정합성 검토

- 검토 입력: `mvp.md`
- 비교 대상: `prd.md`, `addendum.md`
- 검토일: 2026-08-21
- 판정 기준: 원문의 요구 또는 질적 의도가 누락되었거나, 실질적으로 왜곡·약화되었거나, 잘못된 소유 위치로 이동했는지만 기록한다. 단순한 문구 차이, PRD의 합리적 상세화, 구현 중립화는 결함으로 세지 않는다.

## 결론

Context Card, Delta 분류, Evidence Q&A, Tailoring Canvas, 5단계 AI Adoption Level, Evidence Guard, Abstention, Pilot Plan, Human Review, Case Draft, 고정 평가 세트, 검색 방식 비교, 읽기 전용 Wiki 경계는 대체로 충실하게 보존되었다.

남은 정합성 차이는 5건이다. 두 건은 제품의 문제·검증 의도가 명시적 계약에서 빠진 것이고, 세 건은 `mvp.md`의 완료 기준이 기술 부록의 변경 가능한 방향으로 내려가 완료 계약이 약해진 것이다.

## 발견 사항

### GAP-MVP-01 — 원문의 문제 원인과 재사용 문제를 명시적으로 보존하지 않음

- **판정:** 질적 의도 누락
- **원문 근거:** `mvp.md` §2는 (1) 구체적인 사내·사외 사례 부족, (2) 공개 방법론을 프로젝트 맥락에 맞게 조합하는 전문성 비용, (3) 근거와 미검증 가설의 혼동, (4) 실증 결과를 동일 형식으로 기록하지 않아 다음 테일러링에 재사용하기 어려운 문제를 제품의 출발점으로 규정한다.
- **현재 상태:** `prd.md` §2.2 JTBD와 §1 비전은 사용자가 하려는 일을 잘 설명하지만, 왜 이 제품이 필요한지에 대한 위 네 가지 원인 중 특히 사례 부족·조합 전문성·실증 기록 재사용 문제를 명시적인 Problem Statement로 유지하지 않는다.
- **영향:** 후속 UX·Architecture·Story가 Evidence 품질만 최적화하고, 초심자의 방법론 조합 부담과 반복 가능한 사례 기록이라는 원래의 제품 이유를 부차화할 수 있다.
- **정합화 방향:** 향후 PRD 수정 시 문제 진술에 네 원인을 짧게 복원하고, 현재 기능을 늘리지 않은 채 JTBD 및 `Minimum-quality uplift` 원칙과 연결한다.

### GAP-MVP-02 — MVP가 검증하려는 핵심 가정이 성공 계약으로 운영화되지 않음

- **판정:** 질적 의도의 실질적 약화
- **원문 근거:** `mvp.md` §13은 MVP 성공을 장기 플랫폼의 축소 구현이 아니라 “공개 근거로 테일러링 품질을 높이고, 근거 부족을 실증 계획으로 전환할 수 있는가”를 배포 가능한 서비스와 평가 보고서로 검증하는 것으로 정의한다.
- **현재 상태:** `prd.md`는 장기 플랫폼을 범위 밖으로 두고 Abstention/Pilot 전환 지표도 갖췄다. 그러나 §8 성공 지표는 안전성, 완결성, 검색 품질, 재현성에 집중하며, 공개 근거를 사용한 테일러링이 어떤 기준선보다 품질을 높였는지를 판정하는 지표나 수용 기준은 없다. `Minimum-quality uplift`는 원칙으로만 남아 있다.
- **영향:** 모든 현행 지표를 통과해도 원문의 핵심 가정 중 “테일러링 품질 향상”은 검증하지 않은 채 MVP 성공을 선언할 수 있다.
- **정합화 방향:** 고정 AM·ITO Fixture에서 근거 없는/기준선 초안 대비 전문가 루브릭 또는 결정적 필드·근거 적합성 비교를 두어 품질 향상 가정을 검증한다. 속도나 산출량 지표로 대체하지 않는다.

### GAP-MVP-03 — Hugging Face Spaces 데모 URL 완료 기준이 변경 가능한 기술 방향으로 약화됨

- **판정:** 요구의 실질적 약화·소유 위치 부적절
- **원문 근거:** `mvp.md` §11은 “Hugging Face Spaces에 데모 URL을 배포”를 MVP 완료 기준으로 둔다.
- **현재 상태:** `addendum.md` §A는 Hugging Face Spaces를 예정 역할로, §F는 배포 Topology를 Architecture 단계 결정 항목으로 둔다. `prd.md` §7은 공개·합성 데이터 데모만 요구하고, 실제 접근 가능한 Spaces URL을 완료 조건으로 요구하지 않는다.
- **영향:** 다른 형태의 데모 또는 로컬 실행만으로도 PRD 완료를 주장할 수 있어 원문의 공개 데모 배포 약속이 사라진다.
- **정합화 방향:** 특정 호스팅 선택을 변경 가능하게 유지하려면 사용자 승인을 받은 대체를 명시하되, 현재 입력 기준에서는 접근 가능한 Hugging Face Spaces 데모 URL을 릴리스 완료 증거로 유지한다.

### GAP-MVP-04 — RAGAS + 결정적 Custom Metric 평가 보고서가 제품 완료 계약에서 빠짐

- **판정:** 요구의 실질적 약화·소유 위치 부적절
- **원문 근거:** `mvp.md` §9는 RAGAS와 결정적 Custom Metric의 병행을 요구하고, §11은 그 평가 보고서 작성을 완료 기준으로 둔다.
- **현재 상태:** `addendum.md` §A·§D에는 RAGAS가 기술 방향으로 보존되어 있다. `prd.md` FR-19는 LLM 기반 평가와 결정적 검사를 구분하지만 RAGAS 실행 결과가 평가 보고서에 포함되어야 한다는 완료 조건은 없다. 부록 서두는 기술 선택을 검증·변경할 수 있다고 명시한다.
- **영향:** 일반 LLM Judge와 결정적 검사만으로도 FR-19를 충족할 수 있어, 원문이 요구한 RAGAS 결과가 없어도 MVP 완료가 가능하다.
- **정합화 방향:** 현재 입력을 그대로 따를 경우 RAGAS 계열 지표와 결정적 Custom Metric 양쪽의 결과, 버전, 한계를 평가 보고서 필수 항목 또는 릴리스 증거로 둔다.

### GAP-MVP-05 — 최종 문서화 묶음의 완료 기준이 불완전함

- **판정:** 요구 일부 누락
- **원문 근거:** `mvp.md` §11은 PRD, Architecture, 평가 결과, 한계, 재현 절차의 문서화를 완료 기준으로 둔다.
- **현재 상태:** PRD 자체와 평가 보고서·알려진 한계는 `prd.md` FR-19에 일부 반영되고, Docker 재현 방향은 `addendum.md`에 있다. 그러나 Architecture 문서와 재현 절차 문서의 존재·필수 내용·완료 증거를 요구하는 제품 또는 부록의 수용 기준은 없다.
- **영향:** 실행 가능한 컨테이너나 평가 결과는 있어도 제3자가 시스템 구성과 재현 과정을 따라갈 문서 없이 완료 처리될 수 있다.
- **정합화 방향:** 릴리스 산출물 체크리스트에 PRD, Architecture, 평가 결과/실패 사례/한계, 환경·데이터·명령·버전을 포함한 재현 절차를 명시한다.

## 의도적으로 결함으로 세지 않은 차이

- **챗봇 전용 범위:** Knowledge Snapshot 생성·평가·승격·Rollback을 별도 Knowledge Supply Pipeline으로 둔 것은 사용자 결정이므로 결함이 아니다.
- **14주 계획:** 원문의 주차 계획을 PRD 완료 계약에 넣지 않은 것은 “14주 제약 없음” 결정에 따른 것이므로 결함이 아니다.
- **인증·승인자 신원:** 사용자 인증, Reviewer Identity, 조직 공식 결재 증명을 범위 밖으로 둔 것은 사용자 결정이다. Session 사용자의 `accepted` 상태만 기록하는 현재 정의를 결함으로 세지 않았다.
- **Snapshot Release:** Snapshot Release Orchestration을 챗봇 범위 밖으로 둔 것은 사용자 결정이다. 챗봇의 `active_release` 읽기 및 Manifest 일치 검사만 범위에 둔 현재 경계가 적절하다.
- **세부 기술의 부록 배치:** FastAPI, LangGraph, Neo4j, Docker, 공개 모델 Adapter 등은 `addendum.md`에 보존되어 있으므로 누락으로 세지 않았다. 위 GAP-MVP-03·04는 단순 배치가 아니라 원문상 명시적 완료 기준이 비구속적 방향으로 약화된 경우만 지적한다.
